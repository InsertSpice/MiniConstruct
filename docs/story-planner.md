# Story Planner

## Planned Continuity to H3

**Planned continuity is not observed truth.** After Save (or Story Apply), **Planned Continuity** influences ordinary H3 prompt authoring. H3 uses saved Project authority, so unsaved continuity edits must be saved before generation. H3 authoring itself does not watch output. Phase C separately analyzes an explicitly Selected Take and supplies its effective observation as textual evidence.

`H3ContinuityContext` is transient: Sequence Context, Incoming State, Intended Outgoing State, Relationship to Previous, Camera / Shot Intent, applicable predecessor UUID and bounded Story Memory. Canonical Project schema is v17; Workspace remains v1. The browser sends `filesystemProjectId` and `generationId`; the backend reads saved authority by UUID. Older API callers without that identifier use the saved active UUID. Standalone Workspaces receive no Project context. Arbitrary browser continuity text is not accepted as authority.

- **Sequence Context:** sequence-wide planning/world guidance. Preserve relevant constraints without visibly repeating every fact.
- **Incoming State:** hard expected START state unless explicit current authoring requests a change/reset.
- **Intended Outgoing State:** desired END state. Author a plausible transition rather than assuming it at frame zero.
- **Camera / Shot Intent:** shot-level camera authority, subordinate to I2VA/FL2VA/L2VA exact-frame constraints.
- **Story Continuity Memory:** compact planner facts after a Generation, kept separately from Planned Continuity.

Visible-state precedence is `explicit current authoring / Incoming State > predecessor user correction > predecessor model observation > predecessor Intended Outgoing State > trusted relevant Story Memory > stable Character Profile / reference defaults`. Identity says who the Subject is; continuity says what is currently true. If Alice removed her jacket, an older identity Picture or Profile does not restore it. Strict Subject Identity Fidelity follows this precedence too. Historical Pictures and Profiles are not rewritten.

The H3 memory projection uses only the immediate predecessor's **trusted** after-memory: first 1,500 recentSummary characters, then at most eight durable fact texts. Facts linked to participating saved local Subjects rank first; unlinked facts follow in stored order; facts linked only to other Subjects are omitted. This deliberately narrow fallback does not scan the whole Sequence. Open Threads stay planner-only. The current Generation's after-memory is omitted because it describes an intended future outcome. `needs_review` and `legacy_unknown` predecessor snapshots are omitted with a nonblocking warning when they contain summary/fact content. An independent shot omits predecessor memory entirely. Generation 1 has no predecessor.

| Relationship | Ordinary H3 meaning |
| --- | --- |
| continue_previous_shot | Same event/shot, preserving opening framing, camera orientation, Subject state, spatial relationships and momentum without resets or unnecessary establishing shots. Scene Plan, Camera Intent and H3 Shot 1 begin at the best available predecessor ending state; a desired camera change happens after that boundary. A supplied continuation Video is bounded state/motion evidence from whose ending state the target should continue, not a duplicated target prefix. |
| new_shot_preserve_continuity | Same continuous scene/state, deliberately different camera; preserve environment, wardrobe, props and facts without copying the previous composition. |
| match_previous_ending_frame | Exact endpoint matching only with matching endpoint/continuation evidence. Text alone cannot guarantee an exact visual match. |
| independent | No predecessor-local visual/shot assumption. Sequence guidance and explicit current authoring still apply. |

Endpoint warnings check active first-frame-anchor Pictures or payload-backed continuation Videos. An Environment-only Picture is not an endpoint. Same-scene warnings check active environment, continuity-state, identity or first-frame Pictures, or payload-backed continuation Videos. Mode-filtered references do not count. These checks identify available authored evidence, not verified matching media content. Vision-disabled reference metadata can still guide the H3 prompt; the existing warning separately discloses that pixels were not sent to the writer.

**Environment Pictures** preserve location identity, architecture, layout, persistent furniture/fixtures, materials and relevant lighting/palette. They do not automatically control target first-frame composition, camera position/height, lens/framing or Subject placement. Explicit composition/anchor roles and H3 mode constraints can do so; otherwise Camera Intent and the selected authoring path's creative authority control the shot. This improves prompt semantics without promising to eliminate model bias.

When Story Apply creates a new same-scene Generation, it automatically shares its immediate predecessor's Environment-only Pictures for all three continuity relationships. Explicit recommendations are materialized first; equivalent environment content-addressed payload/notes/options are deduplicated and legitimately distinct views survive. Carry chains through new slots using the same existing committed payloads; it never writes duplicate Picture bytes. Independent has no automatic carry but may explicitly recommend an environment. Composition and frame-anchor Pictures are excluded from automatic environment carry. Initial Range, Plan Next, Insert Between and legacy Build follow this rule; existing Replan targets are not implicitly populated by it. Existing mode selection and reference validation still apply; carry does not change modes or turn an environment into a required anchor.

The exact supplied context participates in generated-prompt fingerprints. Changes to saved continuity, the relevant trusted predecessor projection or carried reference set stale an affected selected generated H3 prompt without changing its historical record. Open Threads and unprojected facts do not add H3 dependencies; unrelated distant Generations are excluded. Sequence Context is intentionally shared authority. Existing pre-bridge prompts with newly relevant continuity become stale on comparison.

The opt-in **h3-continuity-bridge** suite contains wardrobe carry and same-bedroom/new-camera cases with synthetic illustrated Pictures. It checks model-facing inputs and normal structural validation, with human review for behavior and no LLM judge. Fixture validation is provider-free; the suite has not been run as part of implementation. Selected Takes and explicit observed-end-state extraction/analysis are implemented. Plan Next receives its terminal anchor’s selected effective observation as read-only evidence; bounded Insert/Replan projections also include active observations. Observed visual state outranks a conflicting intended outcome, while current authoring and nonvisual Story Memory retain their authority. Analysis never auto-mutates Story Memory. Automatic endpoint Picture / short-tail Video handoff is implemented separately in Phase D; long-form visual consistency is not established by offline tests. The opt-in `h3-observed-continuity` suite covers a failed planned jacket removal and an explicit current override. See [observation architecture](execution-orchestration.md#observed-end-state-continuity-20-phase-c).

## Sequence dialogue language

The Sequence Dialogue Language is a single H3 spoken-output setting. Its supported choices are As Written plus Arabic, Chinese, English, French, German, Italian, Japanese, Korean, Portuguese, Russian, and Spanish. When a concrete language is selected, Build Initial Range, Plan Next, Insert, Replan, and dialogue-scoped Revision are instructed to author new exact spoken text directly in that language. Other planning prose stays in its normal authoring language. Existing protected dialogue remains exact authority. Manual dialogue retains source text and can be resolved into an editable exact target output before ordinary H3 compilation; no per-Subject or per-line language state exists.

The opt-in `story-dialogue-language` benchmark suite is the review entry point for story-authored and manually supplied exact-dialogue cases. Run it only with an intentionally configured local provider: `.\.venv\Scripts\python.exe -m miniconstruct.benchmark run --suite story-dialogue-language --profile <profile>`. It is never run by the provider-free test suite.

Story Planner is optional assistance for planning a Project's Sequence. It produces an editable, ephemeral draft; proposed Generation fields are saved only when you explicitly choose **Apply Draft**. Manual authoring, one-Generation **Infer from Previous** / **Revise Plan**, and ordinary Sequence controls remain available. Projects use canonical schema v17 (Workspace remains v1). Story Plan / Premise, Creative Direction, Planning Style, and canonical Subject Character Profiles are Project authoring data saved with **Save**.

**Story Planner Vision** is an optional saved user preference and defaults off. It is effective only when the configured model also accepts images. With it off, Build Initial Range, Plan Next, Insert Between, Replan Range, legacy Build, and visual Story Revision retain relevant Picture roles, notes, Subject mappings, reference recommendations, Character Profiles, Story Memory, and other text metadata without sending Picture pixels. Dialogue-only Revision remains text only. Turn vision on when spatial or environment details would benefit from pixel inspection; existing bounded relevance rules still select Pictures. Model-facing Pictures use disposable RGB JPEG derivatives with a 768-pixel maximum side and quality 84. Canonical saved Pictures and ComfyUI inputs are unchanged. Story Planner reasoning is a separate preference, and ordinary H3 vision remains independent.

**Prepare next ready Generation** finds the earliest Sequence Generation with saved execution authority and runs ordinary Prepare. It never generates H3 or sends to ComfyUI. Ordinary Prepare consumes accepted predecessor native state when applicable; independent and new-shot Generations retain their normal behavior.

## Sequence-level Creative Direction

Project v11 added `storyCreativeDirection`; canonical v17 retains it alongside Character Profiles. It is a compact Project-owned object with four optional, free-text fields: **Tone / Mood**, **Performance / Energy**, **Pacing / Rhythm**, and **Beat Duration / Density**. Each is capped at 2,000 characters; blank strings are valid. The collapsed **Creative Direction** section uses structured controls by default, reusing H3's discrete Tone/Mood and Performance sliders. Tone levels are Auto, Subtle, Moderate, Strong, Intense; Performance style is Restrained, Subtle, Auto, Expressive, Exaggerated; Performance energy is Calm, Low, Auto, Energetic, Intense. Pacing is Very Slow, Slow, Auto, Brisk, Fast; Beat density is Very Sparse, Sparse, Auto, Dense, Very Dense.

Controls encode deterministic semantic presets in fixed control order. Each active value expands to concise Story-planning guidance—for example, low performance energy asks for restrained, low-intensity reactions and movement without making the story slow or boring; brisk pacing asks for regular narrative development; sparse density asks for one primary development with room to breathe. Tone presets guide compatible beat selection, atmosphere, and interpersonal behavior without forcing unrelated content. Performance style describes expression, while energy describes intensity; pacing describes progress across Generations, while density describes what each Generation contains. Auto contributes nothing, so all Auto leaves all four fields blank. Only exact current semantic strings and the original exact short v11 strings (such as `Strong sensuality; subtle tension.`) decode to controls. Arbitrary existing text opens **Custom guidance** and survives byte-for-byte; structured text is not shown as editable Custom prose. **Replace with Custom prose** is explicit, and switching Custom prose back to controls confirms replacement. **Reset Creative Direction** returns controls to Auto and fields to blank, confirming first if Custom prose would be erased. No UI mode or slider position is persisted in canonical Project schema v17. There is no Generate or Rewrite action. Its values are the same for every Generation, persist through reload, Save As/fork, and portable Project export/import, and do not live in browser settings, Generation 1, individual Generations, or Story Memory.

The concepts remain deliberately separate: **Story Idea** says what story is being told; **Sequence Context** supplies broader premise, world, or narrative context; **Story Continuity Memory** says what is true or unresolved; **Creative Direction** says how new Story Planner work should feel and move. Creative Direction is soft presentation/planning guidance, never a factual authority or a generated memory fact. Editing marks the Project dirty but does not invalidate Generation trust; saving the changed canonical direction makes affected ephemeral Story proposals stale.

Build Initial Range, legacy Build, Story Revision, Plan Next, Insert Between, and Replan Range each receive a separately named `storyCreativeDirection` context object. When compatible, they use it for decomposition, performance, pacing, and beat density. Priority remains: structural/signed authority; explicit operation instruction; saved exact/authoritative Generation fields; factual Story Memory or protected boundaries; Story Idea/Sequence Context; then Creative Direction. It cannot broaden a scoped Revision or authorize a boundary, asset, dialogue, or historical-fact change.

Creative Direction is included in the saved context for Story-aware H3 authoring. One-shot H3 continues to use its Main Prompt and normal technical controls without Story planning authority. Offline benchmark fixtures and results can carry/show `storyCreativeDirection`. The earlier Gemma 4 reasoning-on control/guided A/B was run and reviewed for Story planning; it does not establish Story-aware H3 creative quality.

## Project Planning Style

Project v17 adds `storyPlanningStyle` with independent `creativity` (`faithful`, `balanced`, `exploratory`) and `scenePlanDetail` (`concise`, `standard`, `detailed`). The collapsed **Planning Style** section sits beside Creative Direction. New Projects default to **Balanced + Standard**; v1–v16 Projects adapt to those defaults without rewriting on read. The next canonical write persists the field. Save, Save As/fork, filesystem backups, and portable Project export/import preserve it. Changing either control marks the Project dirty and uses normal Save. Reset returns both defaults. Disclosure state is not persisted.

**Planning Creativity** sets latitude for plausible *local connective invention* where story authority leaves room. Faithful stays close to supplied authority, minimizing unsupported props, complications, reversals and implications while still supplying necessary observable action and reaction. Balanced uses existing behavior. Exploratory may add useful character business, object/environment interaction, spatial staging, hesitation, micro-objectives, revealing reactions and small causal complications. It may not contradict saved authority, invent major plot facts, resolve open threads early, consume later Generation events, change protected dialogue, operation boundaries, shot counts or media/reference authority, or add speech merely for variety.

**Scene Plan Detail** controls articulation of the chosen development. Concise is compact but directable, retaining essential action/reaction, causal and spatial change. Standard uses existing behavior. Detailed may describe cause → action → reaction → resulting state with useful attention, posture, gesture, blocking and object/environment interaction. Stillness, silence and restraint remain valid. Detail does not add plot, a fixed beat count, dialogue, duration, shots, camera syntax or H3 timestamps. It does not repeat Camera Intent, Incoming/Outgoing State, Exact Dialogue or stable identity facts. The existing Scene Plan character limit is unchanged.

Creative Direction separately controls tone, performance, pacing and beat density. **Sparse + Detailed** can describe one development richly; **Exploratory + Concise** can choose a more inventive beat and summarize it compactly. Very Dense + Concise can summarize several developments without extra prose. Planning Style is soft guidance below structural/signed operation authority, explicit instructions, protected fields and exact dialogue, current factual Story Memory and continuity, Story Plan/Premise and Sequence Context, Character Profiles and Creative Direction. Current Story Memory outranks a profile's usual trait: a character currently using crutches must keep using them even if normally unaided. Exploratory may shape a profile-consistent reaction but may not invent a conflicting stable trait.

Build Initial Range, legacy Build, Plan Next, Insert Between, Replan Range and Story Revision use one backend policy derived from the saved Project. The default pair adds **no model-facing style text** and does not alter the existing planning messages. In a scoped Revision, style guidance is omitted unless Scene Plan is editable; no style value broadens a Revision scope. Saved style changes invalidate affected outstanding Story proposals through their authority fingerprints, without changing H3 execution state. This feature has provider-free tests; no live quality claim has been made.

## Per-Generation H3 Tone / Performance Controls

Story Creative Direction guides planning. Per-Generation H3 Tone / Performance controls remain separate; Auto lets Story-aware H3 infer from the current Scene Plan, premise, dialogue and continuity. Story-authored new dialogue uses a concrete Sequence Dialogue Language directly; the language tag is not stored in the spoken field. Protected user-authored dialogue remains exact. Distinct vocal events use the existing `Name:` or `Subject N:` textual speaker syntax; punctuation inside one utterance does not create a second speaker. Resolved Spoken Output remains exact audible text only. H3 writes each utterance as `<d>[Language] exact audible text</d>`; the required leading language tag is syntax metadata and excluded from exact spoken-payload comparison. H3 media labels are restricted to the current numbered Picture, Video and Audio manifest, including during Revision and Repair.

**H3 Tone / Performance Controls** are distinct from Story Creative Direction. They are the existing `Workspace.creativeControls.tonePerformance` settings that ordinary H3 compilation already consumes: **Sensuality**, **Drama**, **Horror**, **Tension**, **Romance**, **Whimsy**, **Performance Style**, and **Performance Energy**. Their exact existing domains are `auto/subtle/moderate/strong/intense` for the six tone fields, `restrained/subtle/auto/expressive/exaggerated` for Performance Style, and `calm/low/auto/energetic/intense` for Performance Energy. `auto` is a first-class valid value, not an omitted or coerced value.

Story Planner never proposes or edits these enums. New Story Generations retain the ordinary Workspace `auto` defaults; existing saved values are preserved exactly through Initial Range, Plan Next, Insert Between, Replan, and Revision. Older model replies containing `tonePerformance` are ignored. The shared **H3 Creative Controls** editor is the user override surface: any manually chosen non-`auto` value still enters Story H3 compilation. With `auto`, the H3 writer infers suitable performance from the Story premise, current Scene Plan, dialogue, continuity, and Character Profiles. No Project schema migration is needed.

## Character Profiles foundation

Character Profiles are deliberately small, stable, author-written guidance attached directly to a canonical Sequence Subject's opaque ID. They are not a general Story Bible and they never create a parallel character collection. The UI offers one **Character Profile** free-form field, stored in `characterProfile.notes`. Older Projects retain the structured **Role / Background**, **Personality**, **Appearance**, and **Speech / Mannerisms** fields in saved data and Story context; editing the visible field does not erase them. Each underlying free-text field preserves authored whitespace and is limited to 4,000 characters. Profiles contain no ID, generated history, confidence value, or archetype enum.

The Profile disclosure sits with the existing **Sequence Cast / Narrative Identity** editor for each Subject. It is collapsed by default, uses compact textareas, marks the Project dirty, and is saved only through the normal Project Save / Save As flow. It does not autosave. Canonical profiles survive reload, forks, portable export/import, Generation switching, and dormant/local-subject cycles. Removing a Subject from a Generation does not alter its Profile. If the canonical Subject can be deleted through the existing structural and memory-link restrictions, its Profile disappears with it.

Portable Project envelopes carry `sequenceSubjects` together with the canonical `sequenceNextSubjectNumber` allocation watermark, so deleted high-number Subjects are never reused after import. Older Workspace-only envelopes remain valid and use their existing local allocation path.

Keep the layers separate:

| Layer | Owns |
| --- | --- |
| Narrative Identity | Stable display name and retained aliases for a canonical Subject |
| Character Profile | Stable characterization, background, appearance, mannerisms, voice, and notes |
| Story Continuity Memory | Current or unresolved plot truth, changes, promises, injuries, locations, and relationships |
| Sequence Context | Broader premise, world, or sequence framing |
| Creative Direction | How Story planning should feel and move |

For example, “Alice is usually calm and methodical” is a Profile fact. “Alice fractured her ankle and currently uses crutches” belongs in Story Memory; it controls current planning without rewriting the Profile. Profiles cannot override signed/structural authority, an explicit operation instruction, protected or exact Generation authoring, current or historically valid Story Memory, or exact dialogue.

Story Planner includes only nonblank Profiles for Subjects relevant to that bounded operation, in deterministic canonical Subject number/ID order. Relevance reuses local participation, exact name/alias/technical-label mentions, Story Idea/Sequence Context/instruction, Story Memory links, required Subjects, and historical Subject identity-reference relevance. Build Initial Range may expose all nonblank canonical Profiles because its starting cast is small and broad. Plan Next, Insert Between, Replan Range, and scoped Revision return a long-absent Profile only when the Subject becomes relevant again. A relevant textual appearance Profile and a selected historical Subject Identity Picture may both be supplied; the former is author guidance and the latter is visual evidence. Neither rewrites or reconciles the other.

Profile changes enter the relevant bounded Story fingerprint, so an edit to a relevant Subject stales an outstanding proposal. An unrelated distant Profile is excluded from bounded Plan Next context and does not needlessly stale that proposal. Story operations and Story Memory patches have no Profile mutation fields; editing a Profile also does not change Story Memory. Profiles are Story Planner context only: ordinary H3 prompt assembly never receives a hidden Sequence-profile block. The Profile policy paragraph is emitted only when the operation actually supplies at least one nonblank Profile; blank Profiles add no Profile-specific prompt text.

## Generation-owned Story Continuity Memory

**Story Continuity Memory belongs to Generations. Each Generation stores the story state true AFTER that Generation.** Selecting a Generation shows and edits its own **Story Memory After Generation N**: **Story Summary**, **Durable Facts**, and **Open Threads**. Generation UUIDs identify saved state; ordinals are display labels only. Historical fields are editable. MiniConstruct does **not** use hidden checkpoint/event Story Memory in the canonical design.

The Generation-owned fields introduced in v10 remain canonical under Project v12: every Generation stores `storyMemoryAfter` and `storyMemoryStatus`. There is no canonical `sequence.storyMemory`. The terminal Generation's snapshot is the sole current-memory authority used by Plan Next; **Insert Between** and **Replan Range** instead start only from their selected trusted upstream Generation's `storyMemoryAfter` (or the honest empty initial state at Generation 1). The editor and Save use the selected Generation, which can be different from the terminal Generation.

Two historical schema-v9 layouts are read-only compatibility inputs: the Generation-owned WIP layout and the abandoned temporal layout (identified structurally by `sequence.storyMemory` / `sequence.storyMemoryTemporal`). The latter's checkpoint/event data is migration-only input, never canonical authority. A normal write upgrades legacy Projects to v17 with blank Character Profiles and without retaining hidden temporal checkpoint/event authority.

Normal Save sends explicitly edited memory with `storyMemoryGenerationId` and `expectedProjectFingerprint`. The response contains selected `storyMemoryAfter`, a refreshed `projectFingerprint`, and every Generation's status. Missing/wrong targets and stale fingerprints reject memory saves; the active workspace and memory are written together in one atomic manifest replacement. Saving unrelated fields omits memory, preserving its review status. **Confirm Story Memory** uses the same normal Save path with the selected snapshot and UUID. Save As also applies any selected memory edit to the corresponding cloned Generation.

| Status | Meaning and authoring behavior |
| --- | --- |
| `trusted` | This Generation's saved state is accepted. |
| `needs_review` | An earlier memory or order change may have made this state stale; its saved content remains visible and editable. Edit and Save, or confirm it unchanged. |
| `legacy_unknown` | Older data never recorded this historical state. Empty fields do not mean the story was empty. Fill and Save, or explicitly accept the empty snapshot with Confirm. |

Changing G3's memory marks G3 trusted and later known snapshots `needs_review`, without changing their content. Canonically equal saves do not invalidate successors. Confirming one Generation never trusts the others. Unknown legacy history stays `legacy_unknown` until accepted explicitly. Plan Next requires only the terminal snapshot to be trusted; earlier warnings do not independently block it. The UI also retains its terminal-selection requirement. The compact **Memory Timeline** lists every Generation and status; clicking a row uses normal Generation selection, including its existing unsaved-change handling.

New Projects start with an empty trusted G1 snapshot. **Build Initial Range** starts from that same empty pre-G1 state and writes one sequential `memoryPatchAfter` result for G1 and every new initial Generation; all resulting snapshots are trusted. Manual append and middle insertion inherit a deep copy of the preceding snapshot; inserting before G1 starts empty and trusted. Duplicate receives a deep copy of the source snapshot. Inheritance from an untrusted source starts `needs_review`, never invents confidence or creates another `legacy_unknown` Generation. Middle insertion/duplicate mark existing successors for review; deletion marks the surviving suffix from the deleted position; reorder marks from the first changed position. Existing snapshots stay attached to their UUIDs, and unaffected prefixes retain their statuses. The readable legacy Build path retains its prior predecessor-snapshot behavior for compatibility.

Frozen v1–v16 readers are strict and non-mutating. For v8, only the old `sequence.storyMemory` is known: it migrates to the terminal Generation as trusted. Nonterminal Generations receive empty snapshots with `legacy_unknown`, without invented facts. Versions v1–v7 have no Story Memory at all: the terminal adapts to empty trusted memory and historical Generations remain unknown. Historical v9 layouts are also read structurally: the Generation-owned v9 layout remains readable, while the discarded temporal v9 layout is migration-only input. v10 Projects load with blank Creative Direction; v11 Projects load with blank Character Profiles. The next canonical write emits v17 with blank Scene Plans for older Generations. A read alone does not rewrite a Project. Workspace remains v1.

Story Planner and Planned Continuity are collapsed on a fresh page. No disclosure preferences are persisted.

## Build Initial Range and edit a draft

Save the Project-level **Story Plan / Premise** (`storyIdea`), then choose 2–12 total
Generations while G1 is the sole saved Generation. One local Story provider request
returns the full ordered draft. Each Generation has one editable **Scene Plan**
(`planning.scenePlan`), the compact, directable dramatic bridge between Story planning
and H3 audiovisual execution. It describes what meaningfully develops through
observable action, attention, interaction, reaction, state, or spatial change where
Story authority supports it, instead of stopping at a static pose and abstract intent.
Intentional stillness, silence, and restrained reactions remain valid developments.
The planner may invent plausible local connective detail where user authority leaves
room, but must not consume later-Generation events merely to create activity. Scene
Plans stay concise planning authority, without H3 shot or timestamp syntax; Camera
Intent, Exact Dialogue, and continuity states keep their separate fields.

G1's Main Prompt / Idea remains untouched. New Story Generations keep blank Workspace
`creativeRequest` values. The planner may fill the existing Exact Dialogue / Lyrics
field when speech naturally improves a scene; existing nonblank exact dialogue is
protected unless an explicit Revision scope authorizes a change. For new Generations,
`durationSeconds` may be any 4–15 second value chosen for natural pacing and a meaningful
handoff. G1's saved duration is only the fallback when omitted or invalid. Avoid
stretching small actions to fill a clip. Replan leaves
saved durations intact.

Draft cards put Scene Plan first and keep technical planning details collapsed. Edit
Scene Plans, then Apply. The applied current Generation's Scene Plan remains editable
from Story Planner and saves with the normal Project Save action. Manual edits do not
automatically rewrite later Generations; use Replan Range or another explicit Story
operation when downstream continuity needs repair. No Narrative Brief or extra
character-profile fields are part of this workflow.

**Generate from Story** builds H3 input on the server from saved Story Plan / Premise,
ordered Scene Plans, current planning state, Story Memory, Character Profiles, exact
dialogue, references and normal H3 controls. The Story-aware writer directs those
beats into shots and timing under the official H3 guide. **Generate from Main Prompt**
keeps the one-shot Workspace Main Prompt / Idea as its authority. Story Planner does
not write final H3 prompts. The earlier richer-`creativeRequest` Story approach was
superseded by product testing. The [initial directability benchmark review](story-scene-directability-benchmark.md)
supports this narrow Scene Plan guidance change; it does not establish universal model
quality.

## Story Continuity Memory and Plan Next

Sequence length is independent of model-call batch size. A saved, clean Project with 30, 60, or 100+ Generations can use **Plan Next**. Select the terminal (last) Generation with trusted memory, choose **1–4 new Generations**, optionally enter an instruction, then propose. The anchor is read-only. A nonterminal anchor is rejected. Build Initial Range covers only the one-G1 start; existing scoped Revision is unchanged.

Every Plan Next request includes the persisted Story Plan / Premise, user-authored Sequence Context, separate Creative Direction, Story Continuity Memory, relevant Narrative Cast, and only the anchor plus up to two immediate predecessors. Each local projection includes stable Generation ID, ordinal, Scene Plan, verbatim Exact Dialogue / Lyrics, incoming/outgoing state, relationship, camera intent, mode/duration, local Subjects, and reference metadata. It excludes full Workspaces, generated prompts, execution state, and Creative Control enums. No historical full-Sequence payload is sent.

**Sequence Context** is user-authored premise, instructions, and continuity guidance. **Story Continuity Memory** records selective story progress and what still matters. It does not replace Sequence Context, detailed Generation authoring state, Narrative Cast identity, or H3. The model cannot change Sequence Context through Plan Next.

Each canonical Generation's `storyMemoryAfter` contains:

| Field | Policy limit | Purpose |
| --- | --- | --- |
| `recentSummary` | 6,000 characters | Compact current story position and important developments |
| `durableFacts` | 64 active entries | Facts that remain important beyond the local window |
| `openThreads` | 64 active entries | Unresolved promises, goals, mysteries, or threats |
| Entry `text` | 500 characters, nonblank | One compact fact or thread |
| Entry `relatedSubjectIds` | 32 unique links | Optional canonical Subject IDs |

Entries have stable opaque UUID `id` values. The limits live in `models/story_memory.py`, and the 4-slot/3-context policies in `models/story_operations.py`, for benchmark-driven review. These deliberately bounded collections avoid an accumulating transcript while allowing substantial continuity state. Overflow is rejected, never silently truncated. Updates replace the targeted entry; resolutions remove it. Unmentioned unresolved threads remain active. The model is instructed to avoid incidental details, redundant facts, and contradictory copies; structural validation does not prove narrative truth.

Open **Story Continuity Memory** to edit the selected Generation's Story Summary, facts, and threads. Changes mark the Project dirty and require normal **Save**. A newly added blank row is an editor placeholder omitted from Save; clearing an existing row removes that entry. Save As and filesystem backups retain every snapshot. Memory is never stored in browser localStorage or IndexedDB. Portable active-Workspace JSON export remains an active-Generation format, not a Sequence/memory archive.

Cast projection includes Subjects linked by memory or local Workspaces and Subjects mentioned in supplied story text or the instruction. Current names, retained aliases, and technical Subject N labels resolve to the same stable ID. A memory link to dormant Alice keeps Alice available to planning but does not add her to a Generation or H3 participation. Renaming Alice preserves all memory links. Deleting a memory-linked Subject requires removing its links from every Generation snapshot first.

`localContext` remains limited to the local window. Separately, Plan Next may project a small `historicalReferenceContext` of older **Picture** evidence for relevant canonical Subjects: `subject_identity` and stable `character_comparison_scale` references only. Relevance comes from local participation, Story Memory `relatedSubjectIds`, or exact current-name, retained-alias, and technical `Subject N` mentions in supplied Story text, context, or instruction. This is a backend-local scan of saved reference metadata, not historical prose replay and not generic/vector retrieval. Environments, props, style, composition, Video, and Audio are not historical semantic entities yet.

Historical evidence contains a source Generation/asset pair and safe asset/identity metadata, never the source Generation's request, dialogue, continuity, Workspace, or execution state. Semantic reference deduplication is separate from pixel transport deduplication: exact semantic duplicates (same role, canonical Subject association, and meaningful identity metadata) prefer a qualifying local record, otherwise the newest historical occurrence wins (source/asset IDs break ties); semantically distinct records remain available even when their Picture bytes match. With vision enabled, identical Picture payloads are transmitted once; with vision disabled, metadata remains available but no pixel observation is claimed. Distinct payloads, including useful face/body/outfit/sheet views, remain available. Filename similarity never deduplicates evidence.

Recommendations use `sourceGenerationId + assetId`; the allowed set contains local pairs plus selected historical pairs. Plan Next deterministically drops malformed or unavailable advisory pairs before strict proposal validation and keeps the first valid occurrence of a duplicate pair. Seeing an identity reference neither requires the Subject to appear nor attaches it automatically. Apply revalidates the sanitized set and uses the existing safe reference materializer, sharing the canonical content-addressed payload. Explicit participating Subjects and Subjects required by recommended references become local participants. New Generations start blank, inherit predecessor mode and deterministically carry eligible same-scene Environment Pictures; they do not clone arbitrary controls, dialogue, prompts, or execution state.

## Insert Between

**Insert Between** plans **1–4** new Generations immediately after a selected nonterminal Generation A and before its current immediate successor B. It is shown as its own Story Planner subsection: “Insert after: Generation N” and “Protected next Generation: Generation N+1”, a count, an optional Insert instruction, and **Plan Insert**. A and B are read-only protected boundaries, never proposal cards. The first proposed relationship-to-previous is editable and describes the relationship to A; later proposed slots relate to the preceding proposal. B's existing relationship remains unchanged.

Insert requires a saved, clean filesystem Project, A to be nonterminal with an immediate B, and `A.storyMemoryStatus == trusted`. A `needs_review` or `legacy_unknown` snapshot blocks planning with an explanation; B's memory status does not block use of B's authored narrative fields as a protected downstream constraint.

The sole Story Memory authority is `A.storyMemoryAfter`. The model receives A plus at most two predecessors as `upstreamHistory`, the issued temporary slot IDs, and B plus at most one successor as `downstreamProtectedBoundary`. It does not receive B's or later `storyMemoryAfter`, terminal memory, a historical replay, or the full Sequence. Each response slot has the same authoring fields and `memoryPatchAfter` contract as Plan Next. Patches apply sequentially from A's memory, and Apply persists the resulting per-slot `storyMemoryAfter` snapshots as `trusted`.

Downstream authored fields are narrative orientation, not past truth. The visual/reference cutoff is deliberately conservative: only A or earlier may be source-qualified reference evidence. Relevant historical `subject_identity` and `character_comparison_scale` evidence still uses stable Subject IDs, semantic/pixel deduplication, and optional vision transport; B, B+1, and all later assets cannot be transmitted, recommended, or attached by an Insert proposal.

Apply verifies the signed project fingerprint, A, B, their immediate adjacency, issued slot IDs and order, reference pairs, and patch chain before allocating real Generation UUIDs. It prepares everything before one atomic manifest write, preserves A/B/all existing UUIDs and the active Generation, inserts in issued order, and leaves every B-through-terminal stored memory snapshot byte-for-byte represented by its existing data. Known downstream snapshots transition `trusted → needs_review`; existing `needs_review` stays so, while `legacy_unknown` stays explicitly unknown. It never rewrites downstream memory from inserted state. A stale or invalid proposal writes nothing. Insert draft cards show the collapsed **Story Memory After This Generation** preview. An Insert instruction survives a failed request, and clears only after successful Apply, Discard, or Project/context reset.

## Replan Range

**Replan Range** rewrites Story-owned planning fields for **1–6 existing, contiguous Generations** without creating, deleting, duplicating, moving, or replacing their stable Generation UUIDs. The fifth peer Story Planner section is collapsed initially and provides Start Generation, End Generation, an optional instruction, and **Plan Range**. Selectors expose only valid forward ranges of at most six; ordinals are display labels and UUIDs are the actual authority.

For a target range `C..D`, the immediate predecessor `U` and immediate successor `B` are read-only protected boundaries when they exist. Planning requires `U.storyMemoryStatus == trusted`; a range beginning at Generation 1 begins from an empty `StoryContinuityMemory`. The prompt contains U plus at most two predecessors, every target C..D, and B plus at most one successor. `storyMemory`/`storyMemoryAuthority` are only U's saved memory (or the initial empty state); B/downstream data is orientation prose, never historical memory authority. No terminal-memory lookup, hidden reconstruction, checkpoint/event replay, or whole Sequence prompt is used.

Each response item is addressed by its existing `existingGenerationId` and must cover exactly C..D once in canonical order. It supplies editable Scene Plan, Exact Dialogue / Lyrics (a blank remains deliberate silence), Incoming State, Intended Outgoing State, Relationship to Previous, Camera Intent, reference recommendations, and `memoryPatchAfter`. Patches evolve sequentially from U (or initial state), and every target receives its resulting trusted `storyMemoryAfter`. The first relationship is editable when U exists; it is correctly null for a Generation-1 target. B's relationship is never changed. Only target draft cards render, each with the collapsed projected **Story Memory After This Generation** preview.

Apply verifies a process-signed authority envelope binding Project and operation fingerprints, ordered target UUIDs and display ordinals, U/B adjacency, instruction, initial memory, temporary memory IDs, and explicit permitted reference pairs. A stale, reordered, partial, extra, malformed, or out-of-range response writes nothing. Apply changes only target Story authoring fields and their sequential memory states, preserves target assets, and may use the existing safe helper only to add valid recommended references. Reference sources stop at D: B and later assets are absent from the capability list and cannot suppress an eligible historical stable-Subject identity reference through semantic or pixel deduplication. B-through-terminal memory snapshots remain exactly stored, while statuses change `trusted → needs_review`, `needs_review → needs_review`, and `legacy_unknown → legacy_unknown`. Preparation and the full stale check complete before one atomic manifest replacement; project identity, active Generation, creation identity, and all outside-range data remain intact. A Replan instruction survives a failed request and clears on successful Apply, Discard, or Project/context reset.

The operation endpoints are:

- `POST /api/projects/{project_id}/story-plan/next`: `{anchorGenerationId, requestedCount, instruction?, llm}`.
- `POST /api/projects/{project_id}/story-plan/next/apply`: `{draft}`.
- `POST /api/projects/{project_id}/story-plan/insert`: `{upstreamGenerationId, requestedCount, instruction?, llm}`.
- `POST /api/projects/{project_id}/story-plan/insert/apply`: `{draft}`.
- `POST /api/projects/{project_id}/story-plan/replan`: `{startGenerationId, endGenerationId, instruction?, llm}`.
- `POST /api/projects/{project_id}/story-plan/replan/apply`: `{draft}`.

The model returns `{slots, warnings}`, with a required `memoryPatchAfter` on every slot (an empty patch explicitly preserves state). Every slot uses the existing Story authoring fields, addressed by a backend-issued temporary `planItemId`. Exactly N slots must return in issued order; no existing Generation item or permanent Generation ID is accepted. Extra fields are forbidden. The public proposal adds a backend-owned signed `authority` envelope and `authorityToken`, covering Project/anchor identity, anchor ordinal, fingerprint, instruction, ordered slot IDs, and temporary memory IDs. Editable authoring fields remain outside that signed envelope. These ephemeral proposals require replanning after a server restart; the signing key is process-local, so a deployment with multiple independent worker processes would need a shared authority mechanism.

`memoryPatchAfter` supports only optional `recentSummary` (replacement synopsis), `factUpserts`, `resolvedFactIds`, `threadUpserts`, and `resolvedThreadIds`. Omitted sections preserve existing state; null summary also means no change, while an empty string clears the summary. The supplied `durableFacts` and `openThreads` are read-only current memory and are not response-field names. Upserts use an existing ID in the corresponding collection or one of 16 backend-issued new-entry IDs per collection **per operation**, supplied in `memoryCreationIds`. Any unused issued ID may first appear in any slot; after that, later slots may update or resolve it. Sequential validation retains temporary identity until Apply, then one operation-wide mapping assigns permanent UUIDs consistently across all snapshots. Unknown, duplicate, cross-collection, update/resolve-conflicting IDs and unknown Subject links are rejected. Resolve a thread and create a fact with an unused fact ID; a thread ID can never be used as a fact ID. New canonical entry IDs are allocated only at Apply. The same model call produces the Generation slots and their individual memory deltas; there is no second summarization call.

The review shows N new cards, anchor boundary, and warnings. Each card has a collapsed-by-default **Story Memory After This Generation** section displaying its complete projected state after applying patches sequentially. Generation authoring text and relationships remain editable before Apply. Memory preview is review-only in this foundation: discard and propose again to change draft memory, or edit the resulting Generation after Apply. Discard never applies memory changes. Project/context switches invalidate pending responses using the existing late-response guard.

Apply holds the shared Project transaction lock, rereads terminal authority, verifies signed slot IDs and bounded fingerprint, validates references, authoring fields, Subjects, and **every intermediate memory state**, then allocates UUIDs and prepares all new Generations before one atomic manifest replacement. Slot 1 evolves the terminal snapshot; slot 2 evolves slot 1; and so on. Every new snapshot is independently deep copied and trusted. Final-slot facts or resolutions never flow backward. Active selection and anchor UUID remain unchanged. Validation/preparation failure writes no canonical state; the full-manifest check protects preparation-to-commit from external edits.

The operation fingerprint covers Project ID, terminal-anchor fact, local IDs/order/ordinals and projected authoring fields, Story Idea, Sequence Context, canonical Creative Direction, terminal Story Memory, relevant narrative identity, and each projected historical pair's role, stable Subject association, identity metadata, and payload hash. Unrelated distant edits and irrelevant Pictures do not stale this proposal. A saved Creative Direction edit, memory correction, relevant rename, local edit, or selected historical-reference change does. Legacy full-manifest fingerprints remain available and keep their existing behavior.

Production LLM settings include an optional **Context window** in tokens. This describes model/backend capacity for local estimates and utilization; it does not configure or reload the server. Configure the backend (for example Unsloth) separately to matching capacity. **Max output tokens** is the completion budget, not prompt plus completion total. Context capacity is persisted with the browser's existing settings profile and remains unknown for older profiles until configured. Story planning performs a conservative tokenizer-free estimate using request text, a practical reserve for each transmitted Picture, the configured completion limit, and a safety margin. An estimated overage produces a visible warning but does not block or rewrite the request: the provider's tokenizer and runtime are authoritative. A real provider context failure is surfaced normally without retry, count reduction, staging, truncation, or hidden summarization. Extended 5–12 Initial Build remains one deliberate provider request.

The production benchmark harness adds `build_initial_range`, the focused `story-initial-range` 2/4-total suite, and the opt-in `story-initial-range-extended` matched 4/8/12 decomposition suite. It records source canonical Generation count, requested total, returned items, new Generation count, projected memory states, Pictures, request chars/bytes, raw response bytes, provider token usage, context utilization, and duration. The extended suite adds objective checks for ordered issued slots and projected-memory availability, while human review evaluates useful progression, filler, consistency, and ending quality; it has not yet made a real-model quality claim. `plan_story_next` and `story-next-scaling` retain source lengths 4/12/30/60 and fixed N=3. Offline regressions cover 60-Generation returning-Subject identity recall, historical-pair validity and Apply, payload deduplication, aliases, Character Profile relevance, memory links, non-vision metadata, and exclusion of irrelevant Pictures. Insert and Replan Range have focused deterministic production-path coverage for owned-memory authority, bounded/future-memory exclusion, exact range/slot order, status invalidation, reference cutoff, and atomic stale rejection. No large Replan scaling benchmarks or new live-model quality claim is made. Automatic historical bootstrap and a general Story Bible remain future work.

## Targeted long-form behavioral benchmark

`story-longform` is a qualitative, production-path Story benchmark family. Unlike the 4/12/30/60 scaling suites, it tests durable-fact and open-thread recall, correct resolution, current changing facts, returning and irrelevant Subject identity, Insert/Replan historical correctness, dialogue commitments, and memory hygiene. Each fixture uses an isolated saved Project with roughly 8–9 source Generations; the decisive historical truth is held in owned Story Memory or selected historical identity evidence, not repeated in Plan Next's local context.

Run it manually against a configured provider and model:

```powershell
.\.venv\Scripts\python.exe -m miniconstruct.benchmark run --suite story-longform --profile <profile>
.\.venv\Scripts\python.exe -m miniconstruct.benchmark run --case story-longform-durable-fact --profile <profile>
```

The result records provider/model identity, operation, source and requested counts, request size, measured provider usage when supplied, duration, raw response, parsed proposal, Story Memory before and after each slot, offered/recommended source pairs, structural checks, and Picture transport metadata. It also records `behavioralChecks` with `pass`, `fail`, or `review` evidence. Exact state, IDs, source pairs, future-memory absence, and projected memory changes are deterministic; natural-language continuity remains clearly surfaced for human review. There is no LLM-as-judge, no automatic prose score, and no claim that a model has passed quality evaluation until a real suite run is reviewed.

The offline regression provider is deliberately neutral: it validates request/response plumbing and structural projections but does not infer that a narrative obligation was resolved. Its behavioral failures or review statuses are therefore expected fixture evidence, not model-quality claims.

`memoryHygieneMetrics` reports before/after fact and thread counts, normalized duplicate-text signals, stable/new/resolved IDs, summaries, and linked Subjects without failing legitimate rewording. `referenceMetrics` keeps semantic reference records separate from unique transmitted Picture payloads, so a reviewer can see why Alice was available and Bob was excluded. Insert remains proposal-only in this benchmark: its result includes a safe Apply projection showing trusted inserted memory and the expected `needs_review` downstream status while stored downstream snapshots remain unchanged.

`story-longform-stress` is an expensive, explicitly selected stateful benchmark rather than a broad suite. It starts from one saved three-Generation Project, applies six Plan Next batches, then a historical Replan and Insert (about eight calls and 22 final Generations). It records production Apply/reload evidence, bounded context and cost metrics, memory hygiene, Carol's historical identity-reference transport, and partial-failure artifacts without an LLM judge. The reviewed Gemma 4 reasoning-on result completed G22, passed historical Replan/Insert, and retained long-range Carol identity recall; one Phase-B milestone-obedience behavioral failure occurred, and Story Memory fact growth remains worth monitoring. It remains excluded from `all`; these are observations, not perfect-model claims.

## Scoped Revision and boundary warnings

Select draft Generations, choose fields, enter an instruction, and click **Revise Selected**. The browser sends MiniConstruct the full latest draft, including manual edits. MiniConstruct retains that draft as authority and sends the model scope-aware, read-only context. The model returns selected-field patches, for example `{"patches":[{"planItemId":"<issued UUID>","dialogue":"Alice: We should leave."}]}`. The six scopes are Scene Plan (`scene_plan`), Exact Dialogue / Lyrics (`dialogue`), Incoming State, Intended Outgoing State, Relationship to Previous, and Camera Intent. Reference recommendations are not independently selectable and remain exactly as submitted, including on selected items.

The dynamic response schema contains only `planItemId` and selected fields, all required, with extra fields forbidden. MiniConstruct rejects missing, duplicate, unknown or unselected item patches; unselected fields (even unchanged echoes); missing required fields; and malformed values. Patches map by stable `planItemId`, regardless of response order. They cannot change item order, `existingGenerationId`, Sequence Context or snapshot fields. All selected text fields permit explicit empty strings under their existing authoring limits. In particular, `"dialogue":""` intentionally means silence; omission fails for every selected field. Selected relationship must be explicit: null for Generation 1, a valid enum value thereafter.

MiniConstruct applies validated values to a copy of the authoritative draft, validates full Story structure, and recalculates boundary warnings. Unselected state is never delegated to the model. The API still returns the complete `StoryPlanProposal`, preserving browser replacement, error and late-response behavior. Snapshot/fingerprint checks still run before and after Revision. Instructions remain limited to 8,000 characters. Old full-draft **model** Revision replies are deliberately rejected; saved benchmark results remain readable by comparison tools.

Revision context retains Sequence Context, separate Creative Direction, item count, selected IDs, instruction, and relevant current Narrative Names. Each selected item and its immediate available predecessor/successor appears once in a merged read-only window. Every window includes current Scene Plan, Incoming/Outgoing State, relationship, stable IDs and ordinal for orientation. Dialogue and Scene Plan scopes additionally include dialogue. Visual scopes include Camera Intent and current reference recommendations. Creative Controls have no Story Revision scope. Cast relevance checks all local Story text, including fields omitted from model context, plus Sequence Context and the instruction; mentioned dormant names, retained aliases and technical Subject N labels remain resolvable backend-side without changing the text sent to the model. Creative Direction remains orientation only and cannot change an unselected field.

Source Generation context contains local stable IDs, Subjects, mode and duration. A dialogue-only edit sends no asset metadata or Pictures, even when **Model accepts images** is enabled. Any other selected scope enables visual context: local-window source asset metadata and, when vision is enabled, available Pictures. A committed reference recommended by a window item can supply its particular asset and associated Subjects from a distant source; unrelated assets from that source are excluded. Sources and overlapping windows are deduplicated. With vision disabled, visual scopes retain metadata only. Audio/Video remain metadata-only, and the model must not claim image observations without transmitted Pictures. This deterministic policy requires no new user setting.

For a narrow edit, output size follows selected items and fields; input follows local windows and relevant evidence instead of copying every source Workspace. Global prose and large relevant assets/fields can still contribute context cost. The normal start is Build Initial Range with **2–4 recommended** and **5–12 Extended Initial Build** total Generation choices; legacy Story Build retains its separate readable **2–12** compatibility contract. Plan Next uses the separate 1–4 bounded operation described above.

Deterministic boundary warnings ask you to review an unselected successor after a Scene Plan or Intended Outgoing State edit, or an unselected predecessor after an Incoming State or relationship edit. Camera-only changes warn about the predecessor for continue-previous-shot and match-ending-frame relationships; independent camera edits do not. Warnings are deduplicated, never rewrite neighbors, and are prompts for manual review rather than proof of inconsistency.

## References and media

`participatingSubjectIds` is the ordered, unique set of canonical Subject IDs physically/visually participating in a new Generation; it is not inferred from prose, Story Memory, or cast membership. New Initial Range, Plan Next, and Insert Between items materialize those structural Subjects. For each participant, Apply deterministically carries qualifying legal committed Picture references with role `subject_identity`, selecting the newest legal semantic record and retaining semantically distinct records. `character_comparison_scale` remains recommendation-only because a partial participating set cannot safely imply all linked characters. Reference recommendations are source-qualified optional evidence by `(sourceGenerationId, assetId)`; automatic and recommended pairs deduplicate before UUIDv5 target materialization. No Picture bytes are copied, moved, or rewritten.

Every target asset receives a UUIDv5 derived from the new target Generation UUID and the JSON-encoded source Generation/asset pair. Thus matching asset IDs in two source Generations resolve separately and cannot silently overwrite one another. A final uniqueness check rejects collisions.

Story Planner's `participatingSubjectIds` accepts only exact opaque canonical Subject IDs supplied by MiniConstruct for that operation. The request supplies `availableCanonicalSubjectIds`; names, aliases, and `Subject N` labels are orientation only. Build Initial Range, Plan Next, and Insert Between constrain their response to that allowlist, preserving the existing bounded cast policy. IDs remain ordered and unique; models cannot create Subjects by inventing IDs. With no available canonical Subjects, the field must be `[]` even when Scene Plan or dialogue contains people, animals, or characters. Those characters may still appear naturally in prose. Replan Range and scoped Story Revision preserve existing participants and do not make this field editable. Backend authority validation remains required on Apply.

Participating Subjects enter a new Generation Workspace even before reference selection. Their exact records resolve against canonical Sequence authority. Unrelated local Subjects and references are omitted; no selected participation and no recommendation means no local assets or Subjects. The Sequence cast survives independently. Existing-item recommendations remain advisory and do not alter existing assets or Subjects.

The Identity set selector offers the full Sequence cast. Choosing a dormant Subject copies its stable ID and visible number into the current Workspace before association; Subject 1 remains Subject 1 in a later Generation that previously contained only Subject 2. Cast availability does not itself supply H3 reference participation, transmitted Pictures, or execution inputs. Execution routing is separate authoring-independent state.

## Narrative identity

The canonical Sequence `SequenceSubject` owns `{id, number, narrativeName, narrativeAliases}`. The opaque persistent `id` is the binding key; `narrativeName` is the preferred human authoring name; `narrativeAliases` retains former names for compatibility; `number` defines the stable technical H3 `<Subject N>` label. Workspace `SubjectRecord` remains strictly `{id, number}` structural participation. Workspace save, local dematerialization, Story Apply, Generation duplication, and Project Save As preserve canonical narrative metadata. Standalone Workspaces and portable active-Workspace export have no Sequence narrative authority.

After saving, use **Narrative name** in a grouped Ref2VA Subject section. Named headings and Identity/Comparison selectors show **Alice (Subject 1)**, including dormant Subjects; unnamed Subjects retain **Subject 1**. Naming a new Subject is optional. Once a name is saved, this foundation supports replacement names, not clearing: blank inputs disable Set name/Rename and the helper explains the policy. Retained previous names are an internal compatibility detail, not a normal authoring control. Naming uses the existing saved/clean Sequence guard. Successful responses update canonical presentation and selected-prompt status without replacing local Workspace edits or historical outputs; responses for another Project/Generation are ignored.

Names are trimmed, contain 1–80 Unicode characters, and reject control/format characters and line/paragraph separators. Technical `Subject N` labels are reserved. Names and aliases are unique across the Sequence using Unicode NFKC normalization plus case folding. Renaming **Robert** to **Bob** keeps **Robert** as an alias of the same ID/number. Promoting an own alias removes it from the alias list and retains the displaced primary name. Case-only changes do not add duplicate aliases. At most 100 aliases are retained; a rename exceeding that bound fails atomically rather than dropping older names. There is no independent alias editor.

`PATCH /api/projects/{project_id}/subjects` accepts `{"subjectId":"opaque/id","narrativeName":"Bob"}`. The Subject ID is carried only in the JSON body and is never parsed as a number or filesystem path. The backend validates the full cast and saves one manifest under the ProjectStore transaction lock. Explicit deletion removes the Subject's name and aliases, permitting a later distinct Subject to claim them; this does not establish historical identity with the deleted Subject. Technical numbering remains monotonic and non-reused. Fresh and Full copies preserve the canonical cast and allocation watermark. Removing an identity Picture removes local participation, not the canonical Subject. H3 writer requests use exact stored Subject labels, including sparse casts such as Subject 2 and Subject 5; examples do not authorize renumbering.

Story Build receives the full `sequenceNarrativeCast`, including dormant Subjects and their nonblank Character Profiles. Revision projects relevant cast members from that same committed snapshot as described above. Model-facing cast data contains the stable ID, technical label, and current Narrative Name only. Retained aliases are compatibility/recognition metadata: they are not normal UI authoring controls or generative vocabulary. Narrow backend identity matching may recognize an old name in supplied prose, but MiniConstruct preserves that prose literally and never silently rewrites it to the current name. Newly authored Scene Plan, Exact Dialogue / Lyrics, Incoming/Outgoing State, Camera Intent, and Sequence Context should use current names. Dialogue speaker labels are human-facing text, not identity bindings; technical `Subject N` prose remains supported. Existing nonblank Build fields remain exact authority; Revision still projects only selected scopes/items. Recommendations remain committed `sourceGenerationId + assetId` pairs. Neither migration nor rename rewrites existing authored or generated prose. There is no structured speaker, voice, or audio model; a richer Story Bible remains later work.

For H3 Assemble/Generate/Revision/Repair, the browser supplies request-only `filesystemProjectId` and `generationId`. The server freezes the intersection of canonical narrative metadata and `workspace.subjects` once per operation. Ref2VA receives each current name and canonical `<Subject N>` mapping for interpretation and its full-reference output contract. Base Video modes retain current names as human prose context without a required Ref2VA output label. Retained aliases are not sent to the model and are not used to rewrite Workspace or continuity text; supplied prose is preserved exactly. Names never create additional local Subjects or reference inputs. `/reference-manifest` remains the metadata-only technical input map; `/assemble` includes local current-name context in its richer reference manifest. API clients must supply `filesystemProjectId` for Sequence names; omission preserves standalone behavior.

Narrative Name is the preferred human/Story identity. Names help interpret Main Prompt, Story Scene Plans, continuity and speaker attribution. The strict technical output policy applies only to Ref2VA, whose full-reference grammar defines Subject labels and the `subject_definitions` / `retention_analysis` sections. There, `<Subject N>` is the canonical technical H3 identity: a current name may appear once as natural prose in its valid definition, then structural references use the token. Generate, selective Revision, Repair Format and Assemble diagnostics receive the same Ref2VA policy. T2VA, I2VA, FL2VA and L2VA follow the base Video grammar and receive no instruction to emit Ref2VA Subject labels or sections. Saved authoring stays human-readable; Story Planner continues preferring current names, with Character Profiles available as Story context rather than direct H3 Character Profile prose.

The bundled official Ref2VA guide permits natural prose in `subject_definitions`. A current name may optionally appear once in its own existing definition, preserving the established syntax and reference provenance, for example `<Subject 1> is Alice, the woman in <Picture 1>.` All subsequent structural references use `<Subject 1>`. Base Video modes do not receive a requirement to emit a name in a definition because those grammars have no Ref2VA Subject definition. Never add Ref2VA-only labels or sections to base-mode output. Ref2VA definitions never list retained aliases or invented unnamed placeholders. Subject tokens and Picture tokens retain separate meanings.

Names actually spoken or sung inside literal `<d>[Language] ...</d>` payloads remain verbatim, as does literal visible scene text. In Ref2VA, human `Name:` attribution resolves to the technical Subject token outside the dialogue payload, alongside the official speaker ID. Base-mode speaker attribution follows the active Video guide. Repair preserves action/camera meaning and exact audible wording and introduces no new Subjects. Deterministic repair does not substitute Narrative Names; ambiguous Ref2VA prose goes to the existing narrow model repair with this policy. Canonical identity Picture repair still applies to Ref2VA definitions, including definitions containing an optional current name.

Ref2VA Format Audit continues requiring a literal `<Subject N>` reference in each shot listed by Subject retention. A Narrative Name never satisfies that check. No general name-leakage matcher is added: section boundaries and literal dialogue can be parsed, but natural shot prose does not distinguish a structural character name from an ordinary word, sung/spoken name or unquoted scene text reliably enough. Common-word names such as May and Will therefore do not cause substring findings or automatic replacements. The precise existing Ref2VA retention error remains the deterministic guard; this policy does not promise that Audit detects every name leak outside retention.

Execution authoring fingerprints use version 2 when local narrative mapping exists, including its IDs, labels, names, and aliases. Empty mappings retain the exact version-1 algorithm for unnamed/standalone compatibility. Renaming a local Subject stales old selected prompts and causes selection/Prepare checks to reject incompatible provenance. Renaming a Subject absent from a Generation does not change that Generation's fingerprint. Full-manifest Story fingerprints include every canonical name/alias, so old drafts become stale even for dormant-cast changes. History, previous generated prompts, and saved provenance remain untouched.

## Sequence Subject lifecycle

The Sequence cast is the stable authority for available Subject identities and visible numbers. A Generation Workspace contains only the Subjects structurally materialized for that Generation: an image with the `subject_identity` role uses its selected `subjectIdentity.subjectId`, and an image with the `character_comparison_scale` role uses its selected `comparisonSubjects`. Subject-like metadata on any other Picture role, Audio, or Video is not participation.

When a filesystem Project save removes a Subject's final structural use in the active Generation, its local Subject record is dematerialized. The canonical Sequence Subject remains available and may be materialized later with the same ID and number. Standalone Workspaces retain their existing local-record behavior because they have no higher Sequence authority.

**Delete Subject from Sequence** is an explicit, backend-authoritative action. It is refused while any committed Generation has an identity or comparison/scale relationship to that Subject, or Story Memory links that Subject; no assets are cascaded, reassigned, or altered. Once unused, deletion also removes stale asset-free local copies from every Generation in the same manifest write. Remaining Subject numbers are never compacted or changed, and `nextSubjectNumber` never moves backwards, so a deleted number is never automatically reused. This structural check does not parse or rewrite free-text Subject mentions.

Schema v5 migration merges exact repeated mappings across saved Generations and preserves the highest allocation watermark. Schema v6 migration retains the exact cast and adds null names and empty aliases. Schema v11 adds blank Project-owned Creative Direction; schema v12 adds blank Character Profiles. Schema v16 adds optional Generation `planning.scenePlan`; older Projects receive a blank Scene Plan because historical Main Prompt ownership is ambiguous. Ambiguous ID/number mappings still block content reads and writes with a Sequence cast conflict error, leaving persisted files intact. Reads leave legacy files untouched; successful canonical writes upgrade to schema v17. Workspace schema stays v1. A Story operation's fingerprint includes its saved Planning Style and relevant cast/Profile projection, so relevant profile edits invalidate an older draft while unrelated dormant profile changes do not. Story H3 provenance includes relevant Character Profiles; one-shot H3 provenance does not.

Labels always identify the source Generation. Project responses supply filename/role summaries for all source Generations; labels show the filename's basename and role, falling back to the asset ID only when metadata is unavailable. New-item labels say **Planned reference** and **Will be attached on Apply**; existing-item labels explicitly say they are advisory. Rationale remains visible and no manual reattachment is required for new items. Labels use literal text and do not use stored payload paths.

With **Model accepts images** enabled and a compatible model/endpoint, Build supplies source Pictures as actual vision inputs, labelled by source Generation. Revision uses the relevance-scoped policy above. With vision disabled they contribute metadata only. Audio and Video always contribute metadata, roles, ordering, and user-authored notes only: there is no listening, transcription, decoding, frame extraction, or content analysis.

## Apply, discard, and Project changes

**Apply Draft** remains available after manual draft prose edits and validates the full draft and saved snapshot on action. Draft edits are ephemeral, preserve plan IDs and signed authority, do not mark the canonical Project dirty, and remain available to scoped Revision. A real saved Project change still blocks stale Apply/Revision, and in-flight actions still block duplicates. Apply prepares all resulting Generations and saves the Sequence Context and planning fields together in one atomic manifest replacement. Existing Project and Generation identities, Generation order and creation times, asset mappings, and the active Generation are preserved. Existing Main Prompt / Idea stays unchanged; new Story Generations have blank Main Prompts. Apply writes the exact approved dialogue string directly to the existing `Workspace.dialogue` field for both existing and new Generations; blank remains blank. It creates no second Story dialogue field. New Generations receive stable backend IDs and otherwise blank Workspaces. Plan Next inherits the preceding mode; Insert Between inherits A's mode. Existing modes remain exact. Planned references and required Subjects are carried as described above; previous prompts, continuity, controls, arbitrary anchors, and hidden settings are not cloned. Story-aware H3 generation consumes Story-applied dialogue through the same verbatim path as manually authored dialogue. Draft authoring fields populate their existing canonical destinations. All source pairs, metadata, Subject authority, modes, Workspaces and storage mappings are validated before the single manifest replacement. Apply writes no new blobs, so validation failure cannot leave partially attached assets or orphan payloads.

Canonical editing is temporarily disabled during Apply. A failed Apply retains the draft and leaves the saved manifest unchanged; success adopts the saved Project response and clears transient draft/revision state while preserving the Idea.

**Discard Draft**, approved same-Project Generation switches, and Sequence structural changes clear the proposal and revision state while preserving the Idea. Opening another Project loads its saved Idea; a fresh or legacy Project starts blank. Save As/fork/duplicate retains the Idea, including a submitted unsaved edit. The root `project.json` field `storyIdea` stores the exact text (including whitespace), up to 20,000 characters. Editing it marks the Project dirty and blocks Build, Revision and Apply until Save. Reloading or reopening with a new ProjectStore/server restores it. The page URL remembers only the selected filesystem Project ID, so a browser refresh reopens its saved data; no canonical Idea text is kept in browser storage. Portable active-Workspace JSON export/import includes this Project-level field; filesystem copies and ZIP backups of the Project retain it naturally. The existing portable export remains active-Generation-oriented, not a full Sequence archive. Schema v1–v4 reads adapt to an empty Idea without rewriting files; their next successful canonical write upgrades to v17. Draft items, IDs, warnings, recommendations, selections, and revision instructions remain ephemeral. Conflicting operations ask before discarding draft/pending proposal state; Cancel preserves the draft and Idea. Approved discard happens before the subsequent operation and remains effective even if that operation fails. Late proposal responses are ignored after discard or context reset.

Build requires a saved, clean Project within the Generation limit. Revision and Apply also require clean canonical state. Snapshot protection uses Project ID, updated time, and a fingerprint of the saved manifest, so even persisted edits with unchanged timestamps invalidate an old draft. Revision checks before and after its model call; Apply rechecks before writing. Conflicts return HTTP 409 and require rebuilding or reconciling the draft. Store mutations share an in-process transaction lock; arbitrary non-cooperating filesystem writers and multiple server processes are not supported concurrent transaction mechanisms.

## Developer entry points and limitations

Build requests a separate internal `StoryBuildResponse`: Sequence Context, per-slot planning proposals addressed by `planItemId`, and consistency warnings. It does not request base snapshot fields or `existingGenerationId` echoes. The sparse Build input excludes all three opaque base snapshot values. They remain internal authority and are restored into the public proposal; Revision uses the strict patch contract above while preserving the complete browser/API draft contract. Existing/new slot identity remains visible in Build input. The backend creates the public `StoryPlanProposal` from its initial snapshot, projects only unfilled text and unsaved later relationships, and preserves all saved nonblank authority. Slot IDs must match exactly once in the issued order and count; they are routing keys, not model-created identities. Full-draft replies from the previous contract are accepted only after their entire envelope and identities pass the original strict checks. A mistyped legacy fingerprint is never silently repaired.

The public draft is validated after projection, including relationship structure, warning targets, field types and limits. Structurally invalid responses still fail. Build and Apply sanitize unknown/duplicate reference pairs as before; Revision preserves submitted recommendations. Deterministic incomplete-field warnings use the existing warning contract with equal item/related IDs, displayed as a single Generation label. Up to 12 warning slots are reserved within the existing 256-warning limit, retaining the earliest model warnings that fit. Warnings describe the Build result; manual editing does not automatically clear them.

The frontend editor is in `web/js/story-planning.js`; `miniconstruct/story_planning.py` owns proposal assembly, validation, scoped projection, and warnings. `miniconstruct/models/story_planning.py` defines the ephemeral contracts. `ProjectStore.read_story_snapshot` and `ProjectStore.apply_story_plan` own saved snapshot reads and transactional Apply.

The bounded start routes are `POST /api/projects/{project_id}/story-plan/initial-range` with `{requestedTotalCount: 2..12, llm}` and `/initial-range/apply` with `{draft}`. The legacy `/build`, `/revise`, and `/apply` routes remain for compatible callers. Historical `/build` replies with `creativeRequest` are accepted as legacy Scene Plan prose and never written into Workspace Main Prompt / Idea. Model calls use `response_instruction=None`, excluding the finished-H3-prompt instruction. Every Initial Build action, including 5–12, makes one provider call; responses accept raw JSON or one complete JSON/unlabelled Markdown fence; prose, multiple fences, malformed JSON, and non-object JSON are rejected. There is no automatic repair, hidden continuation, or Story-level retry.

Story Planner does not itself write H3 prompts, render outputs, observe rendered state, persist draft IDs/warnings/recommendations, or add a special Project mode. After Save/Apply, Planned Continuity and the bounded trusted predecessor memory projection feed ordinary H3 authoring; approved Workspace Tone / Performance values are consumed exactly as manually authored controls are. Creative Direction remains soft Story guidance rather than a direct H3 block. Offline service and frontend tests cover these contracts; the [benchmark guide](../benchmarks/README.md#story-planner-suites) describes the production-path Story suites and deterministic fixture identities.

Story Build failures log a concise category, HTTP status, upstream status where available, and a safe detail. JSON and schema failures are separate from identity/authority failures and provider errors. Validation details omit arbitrary input values; provider error bodies are not echoed by Story. No request payloads, image data, keys, or raw model responses are logged by this path. Existing HTTP status semantics remain: invalid requests/store conditions 400 or 422, stale snapshots 409, invalid model/provider output or provider HTTP errors 502, and client timeouts 504. An upstream HTTP 504 becomes 502, with upstream status 504 in the diagnostic.

The exact captured Gemma fixture, legacy envelope checks, compact-response replay, Ref2VA two-image HTTP payload tests, timeout classification tests, and selective Apply/persistence regressions remain executable offline evidence in the test suite.

## Multi-shot planning

Each Story Generation has a positive `shotCount` and an editable **Shot Plan / Camera Intent** (`cameraIntent`). The planner chooses the fewest shots that serve the scene; multiple shots can clarify reaction, reveal, pacing, or cause and effect. The text distinguishes shots in order but leaves exact timestamps and H3 grammar to the H3 writer. Incoming State constrains the opening of Shot 1. When continuing the previous shot, that opening continues the predecessor ending composition before any later cut. Intended Outgoing State constrains the end of the final shot, which is the next Generation’s continuity boundary. Insert Between and Replan Range also honor their untouched outside boundaries.

**Shot guidance** appears inside Build Initial Range, Plan Next, Insert Between, and Replan Range. Auto is the default and retains the planner's existing fewest-purposeful-shots discretion. Prefer N asks for about N meaningful shots per target Generation, allowing the planner to vary the count when the scene benefits. Exact N requires `shotCount` N for every target Generation; a model reply with a different count is rejected before a draft is issued, without retry or coercion. Camera Intent / Shot Plan is instructed to describe the same ordered coverage. This is **per Generation**, never a total-shot budget across the operation. Guidance is operation-local request input and is not saved to the Project or browser; only each applied Generation's normal `planning.shotCount` is saved. Apply synchronizes H3 Setup > Shots, and later manual H3 Setup > Shots remains final H3 authoring authority. Scoped Story Revision does not expose this control.

Applying Build Initial Range, Plan Next, Insert Between, Replan Range, or a Story draft/revision copies each affected planned count to the Generation’s Workspace.shots. A draft alone does not change it. A later manual H3 Setup > Shots edit remains the final H3 authoring choice. If the counts differ, the UI shows an advisory and the H3 writer adapts the planned coverage to exactly the current H3 count while retaining first and final boundaries. No mismatch execution gate is added. Project stays v17; the planning count remains additive/defaulted: a missing historical planning count is derived from the saved Generation Workspace.shots when possible (otherwise one), without rewriting the Project on read.


### Saved Scene Plan, cancellation, and durable context

The permanent **Scene Plan — Current Generation** editor sits near the bottom of Story Planner, after Replan Range and before Planned Continuity, outside every operation disclosure. Planner preferences, Build Initial Range, Story Continuity Memory, Creative Direction, Plan Next, Insert Between, and Replan Range come first. Edit the selected Generation's saved Scene Plan and use normal Project Save; it is the saved bridge to Story-aware H3 authoring. Editing it does not automatically update later Generations; use explicit Story operations such as Replan Range.

Explicit Story **Cancel** aborts the browser request. MiniConstruct watches that request's disconnect, cancels and awaits its exact Story operation, and closes its upstream provider request. This covers Initial Range, Plan Next, Insert Between, Replan Range, scoped Revision, and legacy Build. Apply remains a persistence operation. Cancel preserves the existing draft and saved Project authority; late results are ignored. A third-party model server may still take time to terminate inference after its client disconnects; immediate GPU cancellation is not guaranteed.

Generated Sequence Context must remain durable as the Sequence grows: premise, setting, broad narrative direction, and stable constraints. Requested Generation counts and range boundaries remain structured planning inputs, but they are temporary operation windows, not final Sequence length. The planner must not embed counts or window labels in Sequence Context unless explicitly supplied as user authority. Existing nonblank user-authored context is preserved exactly, including a deliberate “four-part anthology”; no post-generation text rewriting is performed.
