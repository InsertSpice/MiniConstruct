# Story Planner

Story Planner is optional assistance for planning a Project's Sequence. It produces an editable, ephemeral draft; proposed Generation fields are saved only when you explicitly choose **Apply Draft**. Manual authoring, one-Generation **Infer from Previous** / **Revise Plan**, and ordinary Sequence controls remain available. Projects use schema v5. The High-level Sequence Idea is canonical Project authoring data saved with **Save**.

## Build and edit a draft

Save the filesystem Project and any pending canonical edits. Open **Story Planner** in the Sequence panel, enter a **High-level Sequence Idea**, save the Project again, choose **2–12 total Generations**, and click **Build Sequence**. The total must include every existing Generation. Existing Generations remain in canonical order, followed by new draft slots; Build cannot delete or reorder them.

Build preserves every existing nonblank Main Prompt / Creative Request, Incoming State, Intended Outgoing State, and Camera / Shot Intent verbatim. Existing non-null relationships and nonblank Sequence Context are also authoritative, even when the idea conflicts. Blank text fields are planning work to complete, including on Generation 1. New slots receive proposals for all four text fields and a relationship. Completion is a model instruction rather than a guarantee that every returned field is useful. A safe response with blank or whitespace-only planning text returns an editable draft with a warning naming the incomplete fields. The backend does not invent narrative text, copy neighboring prose, or retry the model to fill them. Benchmarks still evaluate completeness separately.

Generation 1 has no predecessor. Later Generations use **Continue previous shot**, **New shot — preserve continuity**, **Match previous ending frame**, or **Independent / new scene**. Build shows sparse saved authority to the model: unfilled text and provisional `independent` relationships are omitted from the draft context. The model must choose unsaved later relationships deliberately. The internal initial draft still uses schema-valid placeholders, but these are not a response template. A saved non-null relationship remains authoritative. If a reordered or older Generation 1 still has a saved relationship, save that Generation with no predecessor before building.

The **Planner request timeout (seconds)** control forwards the existing `llm.timeoutSeconds` setting for Story Build and Revision. It initially shows 600 seconds, even if general LLM settings specify 120, and accepts 1-600 seconds. Explicit values such as 120 or 360 are forwarded unchanged to both operations. The control remains editable and is not separately persisted. It does not change H3 generation settings or the global default of 120. This is the HTTP client inactivity timeout for connect/read/write/pool operations, not an overall generation deadline; slower local multimodal or planner inference may require the longer Story value.

Edit draft Sequence Context and individual fields directly. Typing in the draft does not mark the canonical Project dirty or save it. Assets, Subjects, modes, and settings are read-only planning context. The Idea is limited to 20,000 characters, Main Prompt to 50,000, and context, continuity, and camera fields to 20,000 each.

## Scoped Revision and boundary warnings

Select draft Generations, choose the fields to revise, enter an instruction, and click **Revise Selected**. Revision receives the entire latest draft, including manual edits. It may update only the selected fields on selected items and may recompute their reference recommendations.

The backend validates snapshot identity, item identity, count, and order, then projects the selected authoring fields onto the submitted draft. Unselected fields and items, and Sequence Context, remain exactly as submitted even if the model paraphrases their echoes. Invalid immutable identities still reject the response. Revision instructions are limited to 8,000 characters.

Deterministic boundary warnings ask you to review an unselected successor after a Main Prompt or Intended Outgoing State edit, or an unselected predecessor after an Incoming State or relationship edit. Camera-only changes warn about the predecessor for continue-previous-shot and match-ending-frame relationships; independent camera edits do not. Warnings are deduplicated, never rewrite neighbors, and are prompts for manual review rather than proof of inconsistency.

## References and media

Reference recommendations are source-qualified by `(sourceGenerationId, assetId)`. Equal asset IDs in different Generations remain distinct. Invalid pairs are dropped; duplicate pairs within an item retain their first valid occurrence. On **new** items, every sanitized recommendation means “use this committed source asset”: Apply copies its reference metadata and shares its existing content-addressed Picture payload. No Picture bytes are copied, moved, or rewritten. Kind, filename, MIME type, role, notes, options, subject identity/comparison linkage, and normal asset metadata come from the committed source, never model-supplied replacement metadata. Recommendation rationale itself remains ephemeral.

Every target asset receives a UUIDv5 derived from the new target Generation UUID and the JSON-encoded source Generation/asset pair. Thus matching asset IDs in two source Generations resolve separately and cannot silently overwrite one another. A final uniqueness check rejects collisions.

Only Subjects required by active `subject_identity` or `character_comparison_scale` reference roles are carried. Identical required records are deduplicated; incompatible definitions for the same Subject ID, conflicting visible Subject numbers, or missing authority reject Apply before writing. Unrelated Subjects and references are omitted. No recommendations means no assets or Subjects, even when the inherited mode ordinarily needs references. Existing-item recommendations remain advisory and do not alter existing assets or Subjects.

Labels always identify the source Generation. Project responses supply filename/role summaries for all source Generations; labels show the filename's basename and role, falling back to the asset ID only when metadata is unavailable. New-item labels say **Planned reference** and **Will be attached on Apply**; existing-item labels explicitly say they are advisory. Rationale remains visible and no manual reattachment is required for new items. Labels use literal text and do not use stored payload paths.

With **Model accepts images** enabled and a compatible model/endpoint, Pictures are supplied as actual vision inputs, labelled by source Generation. With vision disabled they contribute metadata only. Audio and Video always contribute metadata, roles, ordering, and user-authored notes only: there is no listening, transcription, decoding, frame extraction, or content analysis.

## Apply, discard, and Project changes

**Apply Draft** validates the full draft and saved snapshot, prepares all resulting Generations, and saves the Sequence Context and planning fields together in one atomic manifest replacement. Existing Project and Generation identities, Generation order and creation times, asset mappings, and the active Generation are preserved. Existing Workspace fields other than Main Prompt remain intact. New Generations receive stable backend IDs and otherwise blank Workspaces. Each appended Generation inherits only the H3 mode of its immediately preceding Generation (including a just-created predecessor). Existing modes remain exact. Planned references and required Subjects are carried as described above; previous prompts, continuity, controls, dialogue, arbitrary anchors, and hidden settings are not cloned. Draft authoring fields populate their existing canonical destinations. All source pairs, metadata, Subject authority, modes, Workspaces and storage mappings are validated before the single manifest replacement. Apply writes no new blobs, so validation failure cannot leave partially attached assets or orphan payloads.

Canonical editing is temporarily disabled during Apply. A failed Apply retains the draft and leaves the saved manifest unchanged; success adopts the saved Project response and clears transient draft/revision state while preserving the Idea.

**Discard Draft**, approved same-Project Generation switches, and Sequence structural changes clear the proposal and revision state while preserving the Idea. Opening another Project loads its saved Idea; a fresh or legacy Project starts blank. Save As/fork/duplicate retains the Idea, including a submitted unsaved edit. The root `project.json` field `storyIdea` stores the exact text (including whitespace), up to 20,000 characters. Editing it marks the Project dirty and blocks Build, Revision and Apply until Save. Reloading or reopening with a new ProjectStore/server restores it. The page URL remembers only the selected filesystem Project ID, so a browser refresh reopens its saved data; no canonical Idea text is kept in browser storage. Portable active-Workspace JSON export/import includes this Project-level field; filesystem copies and ZIP backups of the Project retain it naturally. The existing portable export remains active-Generation-oriented, not a full Sequence archive. Schema v1–v4 reads adapt to an empty Idea without rewriting files; their next successful write upgrades to v5. Draft items, IDs, warnings, recommendations, selections, and revision instructions remain ephemeral. Conflicting operations ask before discarding draft/pending proposal state; Cancel preserves the draft and Idea. Approved discard happens before the subsequent operation and remains effective even if that operation fails. Late proposal responses are ignored after discard or context reset.

Build requires a saved, clean Project within the Generation limit. Revision and Apply also require clean canonical state. Snapshot protection uses Project ID, updated time, and a fingerprint of the saved manifest, so even persisted edits with unchanged timestamps invalidate an old draft. Revision checks before and after its model call; Apply rechecks before writing. Conflicts return HTTP 409 and require rebuilding or reconciling the draft. Store mutations share an in-process transaction lock; arbitrary non-cooperating filesystem writers and multiple server processes are not supported concurrent transaction mechanisms.

## Developer entry points and limitations

Build requests a separate internal `StoryBuildResponse`: Sequence Context, per-slot planning proposals addressed by `planItemId`, and consistency warnings. It does not request base snapshot fields or `existingGenerationId` echoes. The sparse Build input excludes all three opaque base snapshot values. They remain internal authority and are restored into the public proposal; Revision retains its full-draft contract. Existing/new slot identity remains visible in Build input. The backend creates the public `StoryPlanProposal` from its initial snapshot, projects only unfilled text and unsaved later relationships, and preserves all saved nonblank authority. Slot IDs must match exactly once in the issued order and count; they are routing keys, not model-created identities. Full-draft replies from the previous contract are accepted only after their entire envelope and identities pass the original strict checks. A mistyped legacy fingerprint is never silently repaired.

The public draft is validated after projection, including relationship structure, warning targets, field types and limits. Structurally invalid responses still fail. Unknown/duplicate reference pairs are sanitized as before. Deterministic incomplete-field warnings use the existing warning contract with equal item/related IDs, displayed as a single Generation label. Up to 12 warning slots are reserved within the existing 256-warning limit, retaining the earliest model warnings that fit. Warnings describe the Build result; manual editing does not automatically clear them.

The frontend editor is in `web/js/story-planning.js`; `miniconstruct/story_planning.py` owns proposal assembly, validation, scoped projection, and warnings. `miniconstruct/models/story_planning.py` defines the ephemeral contracts. `ProjectStore.read_story_snapshot` and `ProjectStore.apply_story_plan` own saved snapshot reads and transactional Apply.

The POST routes are `/api/projects/{project_id}/story-plan/build`, `/revise`, and `/apply` under the same `story-plan` prefix. Model calls use `response_instruction=None`, excluding the finished-H3-prompt instruction. Responses accept raw JSON or one complete JSON/unlabelled Markdown fence; prose, multiple fences, malformed JSON, and non-object JSON are rejected. There is no automatic repair or Story-level retry.

Story Planner does not generate H3 prompts, render outputs, propagate state automatically, persist draft IDs/warnings/recommendations, or add a special Project mode. Its planning notes do not feed H3 prompt generation automatically. Offline service and frontend tests cover these contracts; the [benchmark guide](../benchmarks/README.md#story-planner-suites) describes the production-path Story suites and deterministic fixture identities.

Story Build failures log a concise category, HTTP status, upstream status where available, and a safe detail. JSON and schema failures are separate from identity/authority failures and provider errors. Validation details omit arbitrary input values; provider error bodies are not echoed by Story. No request payloads, image data, keys, or raw model responses are logged by this path. Existing HTTP status semantics remain: invalid requests/store conditions 400 or 422, stale snapshots 409, invalid model/provider output or provider HTTP errors 502, and client timeouts 504. An upstream HTTP 504 becomes 502, with upstream status 504 in the diagnostic.

The exact captured Gemma fixture, legacy envelope checks, compact-response replay, Ref2VA two-image HTTP payload tests, timeout classification tests, and selective Apply/persistence regressions remain executable offline evidence in the test suite.
